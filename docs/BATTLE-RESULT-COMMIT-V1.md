# Battle Result & Final Commit V1

Status: **ACTIVE-DESIGN — approved design contract for Dungeon Battle result presentation and end-of-battle persistence**

This document extends `BATTLE-SYSTEM-V1.md` and `SAVE-RELIABILITY-V1.md`.

It does **not** replace Battle Core, damage resolution, Speed Queue, action order, skill logic, Pet logic, checkpoint semantics, or reward formulas unless a later explicitly approved implementation task changes those systems.

## 1. Goals

Battle completion must satisfy all of the following:

- the final attack/VFX/death presentation is visible and never cut off by result confirmation;
- Victory/Defeat presentation appears promptly after the terminal action finishes;
- network confirmation happens on the Result screen, not as a blocking visual inside the battlefield;
- a completed battle cannot grant rewards twice;
- a completed battle must not lose rewards because the app/browser closes between completion confirmation and persistence;
- retries after network interruption must return the same completion outcome/receipt;
- Result UI displays confirmed rewards and post-battle progression;
- Battle Core remains the sole gameplay resolver.

## 2. Current production problem

Current Battle V1 reaches a terminal state inside `driveCoreBattle()`, then immediately calls `finishCoreBattle(next)`.

The terminal action currently schedules Hero/Pet/Monster animation and Battle VFX, but `finishCoreBattle()` immediately clears:

- Hero animation;
- Pet animation;
- Monster animations;
- Battle VFX.

This causes the last Basic Attack, active skill, or multi-target skill such as Blade Storm to visually disappear when that action kills the final enemy/enemies.

Current completion also shows `Confirming battle result…` inside the Battle scene while checkpoint/result network confirmation is running.

This contract changes presentation order without changing Battle Core resolution.

## 3. Terminal action presentation contract

When an action produces a terminal Battle Core state:

1. Battle Core resolves the full action normally.
2. Apply the final Battle Core state.
3. Play the final actor animation.
4. Play all VFX generated by that completed action.
5. Show damage/heal/status feedback.
6. Play hurt/death presentation for affected units.
7. Keep all terminal presentation visible for its normal presentation window.
8. Only after the presentation window completes may the battlefield transition to Result.

The Result transition must never clear the same action's animation/VFX in the same render tick that created them.

### 3.1 Multi-target terminal actions

For Blade Storm and other multi-target actions:

- every affected monster receives final damage feedback;
- every monster reduced to zero receives death presentation;
- all related VFX remain visible for the authored action window;
- Battle Result transition waits for the shared terminal presentation window;
- Battle Core outcome remains unchanged.

No extra gameplay turn/action may occur during this presentation delay.

### 3.2 Speed x1/x2

Terminal presentation is presentation-only and follows combat speed scaling.

Use the same shared timing policy as normal combat presentation where practical.

Do not create a fixed terminal delay that ignores x1/x2.

## 4. Result state machine

The Result page owns post-battle presentation.

Recommended Result states:

```text
TERMINAL_PRESENTATION
        ↓
RESULT_CONFIRMING
        ↓
RESULT_READY
```

Optional failure/retry sub-state:

```text
RESULT_CONFIRMING
        ↓
RESULT_RETRY_REQUIRED
        ↓ retry same battleId / same completion intent
RESULT_READY
```

### 4.1 RESULT_CONFIRMING

Show immediately after terminal action presentation finishes.

The battlefield should no longer display `Confirming battle result…`.

Result Confirming may show:

- VICTORY / DEFEAT;
- cleared floor / encounter summary;
- Hero/Pet victory/idle presentation if available;
- reward placeholders/shimmer;
- concise `Confirming rewards…` / `Saving result…` state.

Navigation/actions that could begin another battle remain disabled until the final commit is confirmed.

### 4.2 RESULT_READY

After final commit succeeds, display confirmed values:

- Hero EXP gained;
- Pet EXP gained;
- Gold gained;
- Diamonds if applicable;
- item/material drops;
- Level Up;
- new Pet if applicable;
- floor unlock/progression;
- relevant boss/event/modifier summary.

Buttons become available only in READY state:

- Next Floor;
- Retry Floor;
- Map / Floor Select.

The Result screen must display data from the committed completion result/receipt, not independently reroll or recalculate random rewards.

## 5. Final Battle Commit direction

Target architecture is one logical **Final Battle Commit** boundary.

The client should not require a long chain of sequential network requests after victory.

Preferred logical flow:

```text
last safe checkpoint already persisted
        ↓
Battle Core terminal state
        ↓
terminal presentation
        ↓
Result Confirming
        ↓
Final Battle Commit
        ↓
immutable/idempotent completion receipt
        ↓
Result Ready
```

The implementation may internally perform multiple DB statements, but the client-facing completion flow should behave as one idempotent commit operation where practical.

## 6. Completion identity and idempotency

`battleId` remains the stable battle completion identity unless a later migration introduces an explicit completion request ID.

Requirements:

- the first valid completion creates the immutable completion record;
- retrying the same completed `battleId` returns the existing completion result;
- retry must never re-roll rewards;
- retry must never grant Gold/EXP/items/Pet EXP/floor progress twice;
- a conflicting character/battle identity fails safely;
- UI-level button disabling is not sufficient idempotency protection.

## 7. Safe checkpoint rule

Final commit must preserve Battle V1 safe Action-boundary rules.

Before completion:

- the server must have a valid earlier safe checkpoint;
- final result sequence must be after that checkpoint;
- if the latest required checkpoint has not yet been confirmed, sync that safe checkpoint first;
- do not checkpoint a half-resolved action;
- do not persist readable Battle log history into checkpoint payloads.

Optimization goal:

If the required safe checkpoint is already server-confirmed, do not perform a redundant checkpoint round trip.

## 8. Reward reliability direction

Current production calculates/applies multiple rewards client-side after `completeBattle()` succeeds.

This creates a reliability window:

```text
battle completion accepted
        ↓
client reward calculation/application
        ↓
character/items/run-state persistence
```

If the browser/app is terminated inside that window, completion may exist while reward persistence is incomplete.

The target design must remove that unsafe window.

### 8.1 Required invariant

After Final Battle Commit is acknowledged as successful:

> Re-entering the game must be able to reconstruct the same committed battle outcome and rewards without granting them twice or losing them.

### 8.2 Reward receipt

The completion record/receipt should eventually contain enough immutable data to reproduce the Result screen and recover persistence.

Expected conceptual shape:

```text
battleId
characterId
result
floor
safeActionSeq
completedAt
rewards {
  heroXp
  petXp
  gold
  diamonds
  drops[]
  level/progression changes
  floor unlock
}
postBattleState / recovery metadata as needed
```

Exact schema is implementation-dependent and requires an implementation audit/migration plan.

## 9. Reward authority

Do not silently change current reward formulas as part of Result UI work.

A later Final Battle Commit implementation must decide, explicitly and testably, which reward components move server-side.

Random rewards must have one authoritative result.

No random drop may be rolled once for gameplay and then rerolled for Result display or retry recovery.

## 10. Post-battle state

Result and persistence must use one coherent post-battle state.

Relevant state includes:

- Hero HP/MP carried into next floor;
- Hero level/xp/stat points;
- Pet HP/state where applicable;
- Pet EXP/level;
- Gold/diamonds;
- unlocked floor;
- chest pity;
- inventory/overflow;
- newly granted Pet/item state.

Do not construct Result from one state while saving a different post-battle state.

## 11. Run-state behavior

Victory:

- save the real post-battle HP/MP intended to carry forward;
- preserve Pet carry state per active Pet contract;
- next floor/retry-after-win uses that confirmed post-battle state.

Defeat:

- persist HP=0 as current Battle V1 requires;
- retry creates a fresh full-HP attempt according to existing contract.

Flee:

- preserve existing Battle V1 flee behavior;
- do not infer new reward/progression behavior from Victory rules.

## 12. Navigation locks

Until Result reaches READY:

- Next Floor disabled;
- Retry disabled;
- Map/exit actions that could race persistence disabled, unless explicitly designed as safe recovery actions;
- no second battle can start from the Result screen.

If confirmation fails:

- keep the user on Result;
- provide Retry Confirmation;
- retry the same completion identity;
- never restart/re-simulate the finished battle merely to recover the Result.

## 13. Result UI information hierarchy

Recommended Victory layout:

1. Victory title.
2. Floor/encounter cleared.
3. Hero EXP / Level progress.
4. Pet EXP / Pet progress.
5. Gold / Diamonds.
6. Drops/materials.
7. Level Up / unlocked floor / new Pet highlights.
8. Actions: Next Floor / Retry / Map.

The page should be usable on mobile without vertical overflow hiding primary actions.

Reward reveal animations are presentation-only and must not delay persistence.

## 14. Failure/recovery cases

Must be tested:

- final Basic Attack kills last monster;
- Blade Storm kills all remaining monsters;
- Pet action kills last monster;
- enemy action causes Defeat;
- x1 and x2 terminal timing;
- network loss before completion request;
- network loss after server commit but before response reaches client;
- duplicate completion retry;
- browser/app close while Result Confirming;
- reopen after committed completion;
- inventory full -> Overflow;
- boss chest/drop;
- random junk drop;
- Pet EXP / Pet level-up;
- Hero level-up;
- floor unlock;
- Elite Boss diamond reward;
- stale/missing checkpoint;
- conflicting battle identity.

## 15. Implementation split

Recommended implementation split:

### Phase A — Result Presentation + Terminal Animation Fix

Scope:
- preserve final action/VFX/death animation;
- move confirmation presentation from Battle scene to Result page;
- Result Confirming -> Result Ready state;
- display EXP/Pet EXP/Gold/drop/progression clearly;
- preserve current reward formulas and Battle Core.

This phase should avoid changing reward authority unless required for correctness.

### Phase B — Final Battle Commit / Completion Reliability V2

Scope:
- remove completion/reward crash window;
- immutable reward receipt;
- exact-once reward grant;
- retry/recovery;
- consolidate completion persistence round trips where safe;
- migration/schema changes if required.

Phase B is high-risk and requires focused backend/persistence QA.

## 16. Non-goals

This document does not authorize:

- Battle Core rewrite;
- Speed Queue changes;
- damage/crit/status formula changes;
- skill balance changes;
- Pet AI changes;
- reward rebalance;
- drop-rate rebalance;
- floor progression redesign;
- Phaser gameplay logic;
- removing Battle DOM fallback;
- changing Arena completion semantics.

## 17. QA gates

Before release:

- final-hit animation visibly completes;
- Blade Storm kill-all visibly completes;
- no duplicate reward on repeated completion request;
- no reward reroll on retry;
- Result Confirming never permits a new battle;
- Result Ready values match committed rewards;
- safe checkpoint contract remains intact;
- Battle Core regression tests unchanged/passing;
- save/persistence tests pass;
- build + generated inline-JS syntax guard pass;
- authenticated staging E2E covers completion retry and reload recovery before production cutover.
