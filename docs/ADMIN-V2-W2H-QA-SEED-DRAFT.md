# W2-H — Admin QA Seed (DRAFT design, not implemented)

**Status:** DRAFT, spec AGREED with the Owner 2026-11-03 (see §9, which supersedes §3-§4 and §8 where they differ); Owner will review the real page and adjust. H1 is implemented on branch `feat/w2h-h1-admin-seed-shell` (see §10); H2/H3 not started. **Risk: VERY HIGH** (grants gold/items/pets on Production). Branch + explicit Owner approval before every merge; ships DISABLED.

## 1. Why
`docs/PRODUCTION-QA-POLICY-V1.md` forbids direct SQL/seed writes on Production and requires a supported server-side Admin/QA operation that records an audit event and preserves item ownership/provenance. This slice is that operation. Designated QA identities: `chatgpt`/`gpt1`, `claude`/`claude1`.

## 2. Owner decisions (2026-11-02)
- Admin may pick **any** player (no server allowlist).
- Flow: search username → list all characters of that username → pick a character → list of seedable items.
- Defaults accepted for now (to be tuned after the Owner sees the page): increase-only for level and floor; per-operation caps gold 100,000, materials 99 per stack, 1 item per operation.

## 3. UI flow
1. Username search (build on the Admin V2 Phase 1 Player Viewer).
2. Character list for that username: name, level, gold, unlocked floor, created at, last active.
3. Select a character → seed cards.
4. Every card: input → **server preview (before/after)** → type the **username** and character name to confirm + reason (trimmed 5–300, as W2-D) → submit.
5. Red "PRODUCTION" banner. Soft warning (not a block) when the character was active in the last 24 h or is above Level 15.

## 4. Seed operations
| Group | Operation |
|---|---|
| Level | set level; XP and stat points consistent with the game's own progression formula; increase only |
| Gold | add gold (cap 100,000 per op) |
| Potion | HP/MP potions — **open item:** verify whether stored in `characters.potions` or as `items` stacks |
| Floor | unlock floor; increase only |
| Diamond / Protection Stone | add amount |
| Materials (junk) | add to a stack, max 99 per stack |
| Pet | grant pet with star level |
| Equipment | choose slot / tier / rarity / refine; item generated by the server with the same generator as Reward V2 so stats are valid; 1 item per op |
| Tickets | refill Raid stamina and PvP tickets |

No decrease/delete operations; removal stays with W2-F.

## 5. Safety contract (all operations)
- Kill switch `game_config.admin_seed_enabled` (absent or not JSON `true` = off).
- Audit event `ADMIN_SEED_<TYPE>` with before/after; `requestId` idempotency (repeat → `already_applied`).
- One guarded `db.batch` (audit + ownership event + mutation) with observed-state guard; 409 `item_state_changed` if state moved.
- Items and pets also write `item_ownership_events` (`admin_seeded`) and `item_provenance`.
- Block when the character has a pending operation or a run updated within 30 minutes (same rule as W2-F).
- Carried items beyond 30 slots go to overflow (as W2-G restore).
- Read back and verify progression, inventory, provenance/ownership and audit after each QA seed; record in the QA log.

## 6. Slices
- **H1:** Seed tab shell, username/character lookup, preview endpoints, audit plumbing, flag.
- **H2:** numeric operations (level, gold, potion, floor, diamond/protection stone, tickets).
- **H3:** materials, equipment, pet (needs the item/pet generators and provenance).

## 7. Proposed QA baseline to seed after H2/H3
Level 10 (consistent stats), 20 HP + 20 MP potions, basic non-overpowered equipment, modest gold only if a test needs it, no Diamonds, no extra floor unlock.

## 8. Code audit findings (main d1e0fd5, 2026-11-02, read-only)
**Where data lives**
- **Potions** are `items` rows: `slot_type='potion'`, `extra_json={potionId, quantity}`, potionId in `hp|mp_small|medium|high|full`. `characters.potions` is a legacy/run counter — do NOT seed it.
- **Materials** are `items` rows: `slot_type='junk'`, `extra_json={junkId, quantity}` (shop sells `iron`, `manaOre`; other ids come from junk info).
- **Diamonds are account-level** (`players.diamonds`, shared by every character of the username). **Protection stones** are per character (`characters.protection_stones`). The UI must label this.
- **Gold, level, xp, stat_points, unlocked_floor, raid_stamina, pvp_tickets** are columns on `characters`.
- **Pets**: `characters.pets_json` envelope `{list, dup, skills, skillVersion}`; instance `{instId, defId, level, xp, star, stats}` built by `w45NewPetInstance(defId, instId)`; `active_pet_id` auto-set only when empty. Existing pet writes guard on `pets_json = <observed>`; reuse that guard. Pet ids: sprout, flamekit, sparkpup, ember_fox, moon_hare, hell_wolf, inferno_drake, storm_phoenix. Max star not found in worker code (open).
**Formulas**
- XP to next level = `level*22 + 18`; +5 stat points per level gained; max level 99 (`dungeonV2ApplyCharacterXp`). Seeding Level L from level N: set `level=L`, `xp=0`, `stat_points += 5*(L-N)` (only increase). Level 1→10 = +45 points. No hard coupling between level and floor found (not exhaustively verified).
- `unlocked_floor` drives the shop tier and dungeon tier (`dungeonV2ServerTierForFloor`), so seeding a floor also changes shop stock tier.
**Items / provenance**
- Inventory capacity 30, stack max 99 (`MAIL_INVENTORY_CAPACITY`, `MAIL_STACK_MAX`). `inventoryPlanAddRow` + `mailPlanPersistenceStatements(db, plan, id, characterId, ts, gate, gateBinds)` already handle merge-into-stack, overflow split, `item_provenance` and ownership events; reuse them with `originType: "admin_seed"` and gate on the audit row.
- Equipment: `dungeonV2ServerCanonicalEquipment` (tier comes from a floor; rng required) and, for accessories, `DUNGEON_REWARD_V2.dungeonV2EquipmentItem`; then `dungeonV2ServerRewardItem` builds the `items` row. Empower slots depend on `globalThis.ENHANCEMENT_V2` — must be covered by a test that slots are actually filled (the Raid Wing bug came from a wrong global name).
**Admin infrastructure to reuse**
- Audit: `admin_audit_log` row inserted in the same `db.batch` with guard `INSERT ... SELECT ... WHERE guard`; `buildAdminAuditMetadata({before, after, changedKeys, reason})`; idempotency by deterministic `audit_id` (e.g. `adm-seed-<requestId>`).
- Kill switch pattern: `game_config` key holding JSON `true` (see `adminItemDeleteEnabled`); new key `admin_seed_enabled`.
- Block reasons reusable from `adminItemBlockedReason`: pending `character_operation_receipts`, `character_run_state.updated_at` within 30 min.
- Lookup: `adminSearchPlayers` and `adminGetPlayer` exist, but `adminGetPlayer` returns all characters + all items and writes an `ADMIN_PLAYER_VIEW` audit each call; H1 should add a lighter `adminSeedPreview` instead.
- Admin write actions are registered in the list near `adminDeleteItem` / `adminRestoreItem`; client is `admin-app.js` (`.tab` / `tab-<name>`).
- `validateAdminDestructive` confirms by id; seed needs its own validator (username + character name, reason 5-300).
**Decisions still needed from the Owner**
1. Potion baseline: assume 20 `hp_small` + 20 `mp_small`? (policy baseline says only "HP/MP potion 20+20").
2. Equipment "refine": the code has `enhance_level` (server-authoritative Enhance V2) and empower slots; propose H3 seeds base items only (enhance_level 0, slots as generated) and never seeds enhance levels.
3. Wings: include or exclude from H3.
4. Overflow: the shop blocks purchases while overflow items exist; propose seed does the same (reject `inventory_overflow_pending`) instead of silently overflowing.
5. Pet star: seed star 1 only unless a max-star rule is confirmed.
**Engineering notes**
- Bump the visible version on shipped H1/H2/H3 (project rule); tests must create `item_provenance` / `item_ownership_events` tables in the test DB.
- Register new error codes where the admin client maps them (check `admin-app.js`, not only the game error catalog).

## 9. Agreed spec (Owner, 2026-11-03) — supersedes earlier sections where different
Design mockup: Claude Design canvas "Admin QA Seed (W2-H) — Page Design" (3 boards: character picker, seed cards, preview/confirm).

**Flow and confirmation**
- Pages: (1) username search + character list, (2) seed cards, (3) preview + confirm.
- Page 2 has ONE bottom bar: summary of included cards, reason field, and a single "Preview all" button. No per-card preview/confirm buttons, no confirm button on page 2.
- Page 3 shows the server preview (before/after for every included item), checks, a reason field, a **Back** button (returns to page 2 with values kept) and **Confirm seed**.
- Confirmation needs the **reason only** (trimmed 5-300). No typing of username/character name. Remaining guards: PRODUCTION banner, target chip, mandatory preview, optional yellow warning when the character was active in the last 24 h or is above Level 15 (never blocks).
- One request seeds all included cards atomically: one `db.batch`, one audit row whose metadata lists every sub-change (before/after), one `requestId` (replay -> `already_applied`). If anything is invalid or does not fit, the whole request is rejected.

**Cards (final list)**
- Level (increase only, max 99, xp 0, stat_points += 5 per level gained), Gold (cap 100,000 per request), Unlocked floor (increase only), Diamond (account level, shared by all characters of the username).
- **Removed:** Protection Stone, Raid stamina / PvP tickets.
- **Potion:** dropdown of the 8 game potions (hp|mp x small|medium|high|full), "+ add row", no duplicate type, max 99 per row, max 8 rows.
- **Materials:** dropdown from live `junk_info` (13 rows on 2026-11-03, including Azure `recipe_*` blueprints), same row pattern, max 99 per row, max 8 rows.
- **Pet:** dropdown of the 8 pet defIds (sprout, flamekit, sparkpup, ember_fox, moon_hare, hell_wolf, inferno_drake, storm_phoenix), star 1, "+ add row", max 5 rows, active pet auto-set only if empty. Seeding does not touch the `dup` counters.
- **Equipment** (max 10 items per request, goes to inventory unequipped, enhance level always +0):
  - Search box with English **prefix** search (no Thai search). Catalog: 30 base names (weapon/helmet/chest/gloves/boots/accessory x tier 1-5, tier derived from the name), Wings (azure/robot/skeleton, tierless), 18 Mythic set items (azure/robot/skeleton x weapon/helmet/chest/gloves/boots/accessory(ring)), 3 boss weapons (Spirit Greatsword, Lavalon Sword, Icicle Longsword).
  - Rarity: rare / unique / elite for base gear (1/2/3 option slots); **mythic** (4 option slots) is locked on for Set items and boss weapons. Plain base gear cannot be mythic (a mythic item must carry a `setId` or boss weapon id to be valid in-game).
  - Tier: from the name for base gear; **Set items and boss weapons have no tier in the name** (tier comes from the floor at craft time) so the UI shows a Tier 1-5 dropdown for them.
  - Options: per slot choose the option from `SLOT_POOLS[type]` and the value from `OPTION_DEFS[key].values` (or "random"); duplicates allowed (game rolls slots independently); server validates with `isValidEmpowerOption`. Base stats are computed by the server from tier x rarity (not editable). Boss weapon signature fixed by its definition.

**Caps / inventory rule**
- Rows: potion <= 8, materials <= 8, pets <= 5, equipment <= 10.
- The preview shows "slots used X / free Y" (capacity 30; each potion/material stack and each item uses a slot). If free slots are not enough, or an overflow already exists, the whole request is rejected (`inventory_full` / `inventory_overflow_pending`); never silently overflow.

## 10. H1 implementation record (Ver 1.1.50 after syncing with main 1.1.49; was 1.1.45 when staging-tested, PR #202, branch `feat/w2h-h1-admin-seed-shell`)
Shipped DISABLED (`game_config.admin_seed_enabled` absent = off). Scope: framework + `gold` canary only. Independent review (2026-11-03) found P1-A..D and P2-A..C; all addressed below and awaiting independent re-review.

**API**
- `GET ?action=adminSeedLookup&username=` -> account (diamonds), every character (level, gold, floor, created, last active, `blocked`, `warnings`), `limits`, `operations`. Exact username match; read-only, no audit row.
- `POST adminSeedPreview {playerId, characterId, ops}` -> read-only; `changes` (before/after), `warnings`, `previewHash` (SHA-256 over player, character, `updated_at`, the planned changes and the guarded column values).
- `POST adminSeedApply {playerId, characterId, ops, previewHash, reason, requestId}` -> reason 5-300 trimmed, requestId `[A-Za-z0-9_-]{8,120}`, previewHash must match the recomputed plan (`preview_changed`).
- Flag/auth order (documented behaviour): invalid Admin session -> 401 even when OFF; valid Admin + flag not exactly JSON `true` -> 403 `feature_disabled`; no side effects when OFF. Only the stored string `true` enables; `false`, `"true"`, `1`, `null`, malformed JSON, `True`, whitespace variants, empty are all OFF (tested on all three endpoints).

**Transaction guard (P1-A)** — one `db.batch`: (1) audit INSERT ... SELECT ... WHERE guard, (2) each operation statement followed by a row-count assertion. The guard is evaluated inside the transaction: the character is still exactly as previewed (`updated_at` + every column the operations read), NO `character_operation_receipts` row with `result_json='pending'`, and NO `character_run_state` row updated within 30 minutes (an unparseable timestamp counts as active, fail-closed). If the guard fails nothing is written (no audit, no mutation); the response is the specific reason (`operation_pending`, `character_in_run`) or `character_state_changed`. The preflight check remains only for friendly preview errors.

**Mutation gating** — operation statements apply only when the audit row written by THIS attempt exists: the audit metadata carries a random `attemptToken` and statements test `instr(metadata_json, '"attemptToken":"<token>"')`. A competing request that shares the audit_id can therefore never make a loser's mutation apply.

**Idempotency / payload binding (P1-B)** — audit id `adm-seed-<requestId>`; audit metadata stores `requestHash` = SHA-256 of canonical JSON {playerId, characterId, ops} (keys sorted recursively, reason excluded). requestId reuse: same hash + same character -> `already_applied` (no second mutation, no second audit); anything else -> 409 `request_id_conflict`. A duplicate racing inside the batch lands in the same logic (its guard fails because the winner changed the character) and resolves to `already_applied` or `request_id_conflict`. After a failed batch the same requestId retries cleanly (nothing was written).

**Verified mutation results (P1-C)** — each operation declares `expectedChanges`; after its statement the pipeline appends `SELECT CASE WHEN NOT gate THEN 1 WHEN changes() = ? THEN 1 ELSE json('seed_mutation_rows_mismatch') END`. A mismatch raises inside the batch, so D1 rolls the whole batch back (audit included) and the API answers 500 `seed_mutation_failed`. Never reports success unless audit + every mutation landed. The `changes()` / `json()` assertion is covered by tests on SQLite (node:sqlite harness) and was exercised on a real Cloudflare D1 (STAGING, not production) in scenario 27 of run 41987981229 (see §11). If D1 ever rejected it the failure mode is fail-closed (batch error, nothing written). It has not been exercised on Production.

**Writer coverage of `characters` (P1-D)** — `characters.updated_at` is NOT a complete revision. Audit of every `UPDATE characters` in `workers/` (19 statements incl. the seed's own):
- Bump `updated_at` (17): stat allocation/reset, hero skills, pet economy (3), shop resource + equipment purchase, sell, dungeon reward commit, mailbox reward, blacksmith (V2 and legacy), craft, and the seed itself.
- Do NOT bump: `handleEnterCharacter` (`last_active_at` only) and `handleAttackRaidBoss` (`raid_stamina`, `raid_stamina_updated_at`; protected by its own compare-and-set). Neither writes Gold.
- Design: each operation declares `guard: {column: observed}` (allowlist `ADMIN_SEED_GUARD_COLUMNS`, currently `gold`) and the audit INSERT requires those columns to be unchanged, in addition to `updated_at`. H2/H3 operations must add every column they read to the allowlist and guard it; operations that cannot be guarded by columns (e.g. items) need their own observed-state guard. A static test fails if a new non-bumping `UPDATE characters` writer appears or if any such writer touches `gold`, forcing a review.
- No broad `updated_at` bump was added to existing writers (would change behaviour of the live game).

**Client (P2-B/C)** — Seed tab: page 2 has the sticky bottom bar (summary, reason, Preview all); page 3 shows Player ID, Character ID and name, the server before/after table, the reason (carried over, editable), Back and Confirm. A prominent warning is shown on pages 2 and 3 when the target username is not a QA account (`chatgpt`, `claude`); it never blocks (Owner decision: any player, reason-only confirmation). All dynamic content is rendered with `textContent`; no inline handlers; Preview and Confirm buttons are disabled while a request is in flight; requests time out after 30 s; after a network/timeout error on Confirm the same `requestId` is kept so a retry is safe. Thai texts live in `admin-app.js` `SEED_ERRORS`.

**Tests** — `tests/admin-v2-seed-h1.test.js` (36): flag/auth, lookup, preview read-only, amount validation, activity race (pending, run, unparseable run), field-level guard, writer coverage, requestId binding (amount/player/character), concurrent duplicates, retry after failed batch, attempt-token gating, mutation row-count mismatch (0 rows, too many rows, expected 2, failing SQL), guard-column allowlist, kill-switch variants.

**Audit** — `ADMIN_SEED` row: actor (`player_id` = Admin), target character, metadata {before{playerId, characterId, characterName, ...}, after, changedKeys, reason, requestHash, attemptToken}.

### W2-F / W2-G re-review notes (read-only, current main; no code changed)
- Identity, ownership, equipped/pending/run/unparseable-timestamp guards, stale snapshot hash, stack quantity handling, per-statement guards, audit+event+mutation in one batch: consistent with §22.7 as reviewed in #182.
- **W2F-1 (P2, not changed):** `handleAdminDeleteItem` treats any existing `adm-del-<requestId>` as `already_applied` without checking that the new request targets the same item/quantity. Reusing a requestId for a different item returns a false success (no mutation happens). The UI creates a fresh requestId per attempt, so practical risk is low. Suggested fix: compare `target_id` (and quantity) with the stored audit row, as H1 does with `requestHash`.
- **W2FG-2 (P3, not changed):** the item statement's row count (`results[2].meta.changes`) is checked after the batch but a mismatch cannot roll back the already-inserted audit/event rows. The three statements carry textually identical guards inside one serialized transaction, so the mismatch should not be reachable; adopting H1's in-batch assertion would make it impossible by construction, but only after P1-C is proven on D1.
- **W2G-3 (P3, limitation):** a restore that has to use a new item id (original id taken) writes no `item_provenance` row; only the admin viewers read provenance (game logic does not), and the ownership event and audit record exist.
- Cross-scope: audit ids are namespaced (`adm-del-`, `adm-res-`, `adm-seed-`) on one primary key; flags are independent (`admin_item_delete_enabled`, `admin_seed_enabled`); all entry points check the Admin bearer session before the flag; H1 now reuses the W2-F/G activity helpers (single implementation).
